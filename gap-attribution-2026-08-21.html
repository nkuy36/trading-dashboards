batch_run change_pct / top-level open field — CONFIRMED BUG, worse than previously documented
The top-level 'open'/'change'/'change_pct' fields on a 2-bar daily pull blend bar[0].OPEN (yesterday's open, not close) with bar[-1].close (today's close) — produced nonsensical single-day swings like GLD +3.24%, IBIT +7.24%, COPX +8.43%, TEM +17.56%, TMC +22.19% that don't match any real one-day move and directly contradicted the already-published 5PM scan for the same names. All reported % moves in this report are computed exclusively from last_bar.close (today's daily bar) vs last_bar.close (live 5-min bar) — never from the aggregate open/change/change_pct fields. This is a stricter application of the known [[batch_run OHLCV 2-day blend bug]] than previous scans used — worth hardening the prompt's PRICE PULL METHOD to explicitly ban the top-level fields, not just change_pct.
No-timeframe batch_run call returns STALE data for individual stocks (new finding)
Calling batch_run(get_ohlcv, count=2) with no explicit timeframe returned fresh live minute-bars for the 58 ETFs, but returned byte-identical stale daily-bar data for all 71 Tier1/2 stocks on the first attempt (same timestamps, same OHLC as the explicit D-timeframe pull). Fixed by explicitly requesting timeframes:['5']. Recommend the prompt's PRICE PULL METHOD explicitly require timeframes:['5'] for the live/AH pull rather than relying on an implicit default, since the default's behavior was inconsistent between ETFs and stocks in the same session.
